# Пилот центрального сервера на 1–2 ПК

Цель: пройти путь от пустого Railway до первого оплаченного сеанса и убедиться, что деньги сходятся. Идёт параллельно
основной системе клуба, на одном-двух местах. Запуск сервера и переменные описаны в [`server/README.md`](../../server/README.md)
(«Docker и развёртывание», чек-лист Railway); здесь — порядок пилота и приёмка.

Нужно: аккаунт Railway (тариф Pro — для бэкапов volume), домен клуба или `*.up.railway.app`, 1–2 ПК с Windows и правами
администратора, владелец клуба под рукой (PIN, тарифы).

## 0. Решить до старта

| Что | Пилот |
|---|---|
| Ключ регистрации агентов | случайная строка от 24 символов, не `dev-club-key` |
| PIN владельца | лучше не задавать: при пустом `Club__OwnerPin` сервер создаст случайный PIN в файле `/app/data/owner-pin.txt` (в логе только путь, D-77). Если задавать — 4–8 цифр и не `0000`, а после первого входа сменить в кассе и удалить переменную |
| Часовой пояс клуба | `Club__TimeZone` (по умолчанию `Asia/Tashkent`): по нему считаются дни тарифов и отчётов |
| Каталог игр и товаров | стартовый набор из образа (`seed/games.example.json`, `seed/products.example.json`) или свои файлы (README, «Каталог игр и товаров», Q-5) |
| Домены | API (`https://api.<домен>`) и касса (`https://<касса>`): нужны заранее, касса попадает в CORS |

## 1. Сервер

1. По README: проект Railway (EU West), PostgreSQL, сервис из репозитория, volume на `/app/data`, переменные, домен.
   Для пилота с готовыми каталогами добавьте `Catalog__GamesSeedPath=seed/games.example.json` и
   `Catalog__ProductsSeedPath=seed/products.example.json`.
2. `GET https://<api>/health` → `200`; в логах нет ошибок миграций. При пустом `Club__OwnerPin` в логе строка
   «owner created with a generated PIN, written to /app/data/owner-pin.txt»: прочитать PIN командой
   `railway ssh -- cat /app/data/owner-pin.txt` (CLI один раз попросит добавить SSH-ключ), войти в кассу и сразу сменить PIN —
   файл удалится при следующем старте. Пока владелец входит со сгенерированным PIN, каждый старт напоминает об этом в логе.
3. **Проверка `X-Real-IP`** (от неё зависят лимиты неверных PIN, D-76). Один неверный PIN с известного публичного адреса, с
   поддельным заголовком:

   ```bash
   curl -s -o /dev/null -w '%{http_code}\n' -X POST https://<api>/api/v1/admin/login \
     -H "X-Real-IP: 203.0.113.7" -H 'Content-Type: application/json' -d '{"pin":"9999"}'
   ```

   В логе Railway строка `Wrong staff PIN from <IP> for club <id>` должна показать **ваш** публичный адрес — край перезаписал
   заголовок, всё в порядке. `203.0.113.7` — заголовок берётся от клиента и лимит по адресу обходится: убрать
   `Proxy__ClientIpHeader` и разобраться с прокси Railway. Приватный адрес или `100.64.x` — все клиенты считаются как один адрес
   прокси (пять неверных PIN откуда угодно закроют вход новым браузерам на 15 мин): тоже разобраться до пилота. Шесть запросов
   с разными поддельными адресами и шестой `429` этого не различают.
4. Volume: `data/jwt-signing-key.pem` и `data/pin-pepper.key` создались при первом старте. Сделать бэкап **до** пилота
   (база + `data/`, README «Резервное копирование») и один раз проверить восстановление.

## 2. Касса

Касса — статика (`apps/admin`), маршрутизация через `#`, правил перенаправления не нужно.

```bash
VITE_ADMIN_API=https://<api>/api/v1 pnpm --filter @clubshell/admin build     # результат: apps/admin/dist
```

Опубликовать `apps/admin/dist` на любой статический хостинг с HTTPS. Origin кассы (`https://<касса>`, без слэша в конце) записать в
`Cors__AllowedOrigins__0` сервера и перезапустить сервис. Войти PIN владельца и настроить: тарифы и зоны, бонусы пополнения, группы
клиентов, кассиров («Персонал»). Ключ API (`ck_…`) для пилота не нужен.

## 3. Агент на ПК

```powershell
ClubShellSetup.exe /quiet SERVERURL=https://<api> CLUBAPIKEY=<Club__EnrollmentKey> KIOSKUSER=club INSTALLSHELL=1
```

`baseUrl` (`…/api/v1`) и `wsUrl` (`wss://…/ws/agent`) выводятся из `SERVERURL`, ключ пишется в `agent.json → server.clubApiKey`.

**Установщик клуба «под ключ».** Bundle можно собрать с вшитыми адресом сервера и ключом клуба: `dotnet build installer/wix/ClubShell.Installer.wixproj -c Bundle -p:MsiPath=<msi> -p:DefaultServerUrl=https://<api> -p:DefaultClubApiKey=<ключ>`. Такой exe ставит рабочий ПК двойным щелчком; храните его только в клубе (с ним можно поставить ПК в очередь на одобрение). Эталон для образа: после установки `tools\scripts\prepare-image.ps1` останавливает агента и стирает регистрацию. Перед сборкой без ключа удалите `installer/wix/obj/Bundle`: WiX переиспользует промежуточные файлы.

**Проще скриптом.** `tools\scripts\pilot-install.ps1` (PowerShell от администратора, рядом с `ClubShellSetup-*.exe`) спрашивает адрес сервера и
ключ клуба (ключ вводится скрыто), проверяет `GET /health`, ставит ClubShell и следит за регистрацией: по журналу агента пишет по-русски, что
происходит и что делать (ПК ждёт одобрения в кассе → «Карта» → одобрить; ПК зарегистрирован).

**Эталонный ПК для образа.** Если с этого ПК снимается образ, запустите скрипт с `-ForImage`: после установки агент останавливается, а файлы
регистрации (`agent-identity.json`, `secure\agent.tokens`, `secure\hwid.fallback`) удаляются. Иначе клоны унаследуют регистрацию эталона и станут
одним ПК для сервера. Если эталон успел появиться в кассе, удалите его там до снятия образа; агент не запускайте до снятия образа. Клон при первом
запуске регистрируется сам и ждёт одобрения, как любой новый ПК.
`prepare-image.ps1` удаляет и то, что эталон накопил за время проверки: офлайн-базу игроков (`cache\offline.db` с хешами паролей и
незавершённым офлайн-сеансом, который иначе воспроизвёл бы каждый клон), журналы, скачанные обновления, историю сбоев, токен оболочки,
кэш сохранений и настроек игроков. Без ключа обновлений (`Agent\update-public.pem`, ставится с 1.0.15) он отказывается работать, а
перед удалением показывает сервер и последние 4 символа ключа клуба из `agent.json`: сверьте их с `Club__EnrollmentKey` на Railway.
Повторный запуск установщика с вшитым ключом заменяет ключ и адрес сервера в уже существующем `agent.json`, так новый ключ попадает на эталон.
**Сброс профиля между игроками.** `enable-kiosk-autologon.ps1` выключает его (до 1.0.15 после сброса появлялся рабочий стол
Windows). С 1.0.15 агент после сброса заново пишет оболочку и ограничения в новый профиль и закрывает его explorer.exe. Включите
сброс на пилоте `tools\scripts\set-profile-reset.ps1` (выключить: `-Off`), проверьте: войти в Steam, завершить сеанс, через 1–2 минуты
войти снова — Steam не помнит аккаунт, рабочего стола нет. Только после этого снимайте образ со сбросом.
**Номер места по имени Windows.** Эталону дайте нейтральное имя (например, `CLUB-REF`). Каждый клон после первой загрузки ждёт одобрения;
переименуйте его Windows по месту (`PC-17`, `pc17`, `ПК-17` или `17`) и перезагрузите: пока ПК ждёт одобрения, он переезжает на этот номер
и имя `PC-17`, если номер свободен. Новый ПК с таким именем сразу получает этот номер. Потом одобрите его в кассе.
**Образ через club-server** ([deepunites/club-server](https://github.com/deepunites/club-server), заливка Windows по PXE, игры с
TrueNAS на `G:`). Эталон готовится в режиме аудита (Ctrl+Shift+F3 на OOBE): драйверы, Steam (локально на `C:`), помощник
`ClubDisklessHelper`, затем ClubShell-Setup, одобрение в кассе и ENABLE-KIOSK (перезагрузку пропустить). Дальше `PREPARE-IMAGE`, удалить
эталон в кассе и сразу, без перезагрузки, `sysprep /generalize /oobe /shutdown /unattend:<unattend>` (club-server не принимает
образ без generalize), снять `install.wim` и опубликовать его в панели club-server. При заливке club-server пишет имя Windows из имени
места (`PC-17` по умолчанию) — ClubShell по нему сам ставит ПК на место 17, поэтому номера мест в панели club-server должны совпадать
с залом. Агент не трогает `G:`, пока установлен `ClubDisklessHelper` (`docs/DISKLESS.md`). Связка с sysprep пока не проверена на
стенде: после generalize агент заново задаёт пароль учётной записи киоска (машинные ключи DPAPI меняются) и автовход; первый образ
залить на 1–2 ПК и проверить, а если ПК не вошёл в киоск сам — `ENABLE-KIOSK` с копии папки на `C:`.
Новый ПК ждёт одобрения: в кассе (карта) он появляется как ожидающий; владелец одобряет его и задаёт номер и зону. После этого
агент получает токены, на карте место «свободно».

## 4. Приёмка (записать результат каждого шага)

1. Касса: открыть смену (наличные на начало).
2. Создать клиента, выдать временный пароль; пополнить на 100 000 сум наличными: бонус по порогам, запись в леджере.
3. На ПК: вход игрока по логину и паролю (и по карте, если привязана); запуск игры из каталога.
4. Сеанс: цена в киоске совпадает с расчётом кассы (`adminQuote`); продление; завершение — возврат пропорционально неиспользованному.
5. Команды из кассы: сообщение, блокировка, разблокировка, перезагрузка.
6. Офлайн: отключить сеть на ПК на минуту — вход и сеанс продолжаются; вернуть сеть — данные синхронизируются, деньги не
   удвоились.
7. Закрыть смену: Z-отчёт сходится с наличными пополнениями и возвратами; «Контроль» и «Отчёты» показывают то же.
8. Перезапуск сервиса на Railway: агенты переподключаются сами (около минуты простоя), открытый сеанс не потерян.

Критерий готовности: все шаги прошли, баланс клиента = сумма строк леджера, в логах сервера нет 5xx.

## 5. Откат

Удалить агента: `ClubShellSetup.exe /uninstall /quiet`. Сервер и данные пилота отделены от основной системы клуба; бэкап перед пилотом —
точка возврата для базы и `data/`.

## 6. Ограничения пилота (сознательно)

- Обновления агента не раздаются (`getUpdateManifest` всегда `204`): новую версию ставить вручную.
- Нет магазина и заказов, чата, бронирования, турниров, онлайн-пополнения: соответствующие операции отвечают `501`, агент их не
  вызывает.
- Значения по умолчанию у открытых вопросов (DESIGN §12.3). Лимит неверных PIN (D-76, Q-10 закрыт): касса, где уже входили с
  верным PIN, считается отдельно, поэтому чужие неверные PIN с IP клуба её не блокируют. После деплоя D-76 каждую кассу один раз
  перезайти (выйти и войти), чтобы клуб начал ей доверять; новый браузер при атаке может ждать до суток. Смена PIN сотрудника
  закрывает его входы на других устройствах (D-77).
- Синхронизация мест с `club-server` (диск-лесс) не в v1: номер места в кассе ставят вручную такой же, как в панели diskless.
